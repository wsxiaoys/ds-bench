# Reactive Project Task Board with Manual React Query Cache Management ## Background You are working on a Wasp (wasp.sh) full-stack app called **taskboard**. Wasp compiles a declarative `main.wasp` file together with your React/Node code into a full-stack app, using Prisma for the database and React Query for client-side data fetching. Wasp automatically invalidates a Query's cache whenever an Action that declares the *same* Entity runs. This automatic, entity-based invalidation is convenient but coarse: it does not understand *derived* or *relational* data, so a computed Query that depends on another entity only through a relation will NOT be refreshed automatically. Your job is to build a small task board that relies on automatic invalidation where it works and falls back to explicit React Query cache management where it does not. A Wasp project skeleton already exists at the project path. You must implement the data model, the Operations, the database seed, and the page. ## Requirements * Model two entities in the Prisma schema: a **Project** (has a name and many tasks) and a **Task** (has a title, a done flag, and belongs to a Project). * Implement a Query `getTasks` that returns every task (with its id, title, done state and project id). * Implement a computed/derived Query `getProjectStats` that returns, for every project, an object with the project's id, its name, the total number of tasks in that project, and the number of done tasks in that project. * Implement an Action `addTask` that creates a new task in a given project, and an Action `toggleTask` that flips a task's done state. * Build a single page (mounted at `/`) that lists every project together with its live statistics, lists all tasks, lets the user add a task to a project, and lets the user toggle a task's done state. Every displayed value must update reactively after an Action, WITHOUT a full page reload. * Provide a database seed that populates the initial board (see the hint below for the exact required data). ## Implementation Hints * Wasp automatically invalidates a Query whenever an Action that shares one of its declared entities runs. Use this for the plain task list, but remember it only fires on exact entity overlap: declare the entity `getTasks` reads so Wasp keeps it fresh automatically. * `getProjectStats` is an intentionally decoupled aggregate: it MUST be declared so that it depends only on the `Project` entity (do NOT add `Task` to its entity list). Because of that, adding or toggling a task will NOT automatically refresh it. You must keep it up to date on the client yourself using React Query's cache mechanisms: obtain the `QueryClient` (react-query is bundled with Wasp and importable from `@tanstack/react-query`) and invalidate/refetch the stats Query after the relevant Actions. A Wasp client Query object exposes its cache key via its `queryCacheKey` property, which you can use as the react-query query key. * Compute the derived statistics from the database (e.g. via the Project entity's Prisma relation / relation counts); do not maintain a separate hand-rolled counter table. * Use a local SQLite database (the default dev database). Run `wasp db migrate-dev` after changing the schema so it is applied, and commit the generated migration. * Add exactly one Wasp database seed named `devSeed` (declared under the app's `db.seeds`). It must be safe to run repeatedly and must always leave the database in exactly this state: a project named `Work` containing two tasks titled `Ship release` (done) and `Write docs` (not done); and a project named `Home` containing one task titled `Buy groceries` (not done). Running it should clear any prior projects/tasks first so the result is deterministic. The seed is run with `wasp db seed devSeed`. * Project path: /home/user/taskboard * Start command (run from the project path): `wasp start`. This serves the web client at http://localhost:3000 (the API server runs on port 3001). The first build can take a while before the page becomes available. * The page must render the following stable, machine-checkable markers so the UI can be inspected reliably (attributes are on the element whose text is read): * For each project, show its name, and an element with attribute `data-testid="stat-total-<projectId>"` whose text content is exactly the project's total task count as a number, and an element with attribute `data-testid="stat-done-<projectId>"` whose text content is exactly the project's done-task count as a number. * For each task, an element with attribute `data-testid="task-<taskId>"`, and a clickable button with attribute `data-testid="toggle-<taskId>"` that toggles that task's done state. * For each project, a clickable button with attribute `data-testid="add-task-<projectId>"` that adds a new task to that project (the new task's title may be any non-empty string). * `<projectId>` and `<taskId>` are the numeric database ids of the project and task.
