# Deterministic Discrete-Event Scheduler for a Multi-Server Queue (libGDX Headless) ## Background Build a deterministic discrete-event simulation (DES) engine for a multi-server queueing system. The engine must run inside a libGDX **headless** application (no OpenGL/GL calls) and be driven by the application's tick loop. Simulation time is *virtual* (there is no wall-clock timing): the passage of time is defined entirely by the events pending in an event queue. Events are scheduled into libGDX's binary heap (`com.badlogic.gdx.utils.BinaryHeap`) and are always processed in a strict, fully-specified order. ## Requirements Implement a program that reads a scenario description from a text file, simulates the queueing system to completion, and writes a deterministic report to an output file. The system has `N` identical servers (indexed `0..N-1`) and a fixed set of jobs. Each job has an arrival time and a service duration. There are three event types: `ARRIVE`, `START_SERVICE`, and `DEPART`. A queue discipline (`FIFO` or `SJF`) decides which waiting job is served next when a server becomes available. ### Event ordering (strict, multi-key) Events pending in the heap must be popped in this exact total order: 1. **ascending event time**; 2. then by a strict **event-type priority**: `DEPART` before `START_SERVICE` before `ARRIVE`; 3. then by **FIFO insertion sequence**: a global counter, starting at 0, incremented by 1 each time any event is pushed into the heap; the event pushed earlier is processed first. The initial `ARRIVE` events are pushed once, up front, in the order the jobs appear in the scenario file (so the first job's `ARRIVE` gets sequence 0, the next gets 1, and so on). ### Simulation semantics * **ARRIVE(job)**: the job enters the waiting queue (record its enqueue order), then run dispatch. * **Dispatch** (run at the end of processing every `ARRIVE` and every `DEPART`): while at least one server is idle and the queue is non-empty, select an idle server and a waiting job, remove the job from the queue, reserve that server, and push a `START_SERVICE` event for that (job, server) pair at the current time. Repeat until no idle server or the queue is empty. * The selected server is always the idle server with the **smallest index**. * The selected job depends on the discipline: * `FIFO`: the waiting job that entered the queue earliest. * `SJF`: the waiting job with the smallest service duration; ties broken by the job that entered the queue earliest. * **START\_SERVICE(job, server)**: record the service start time (= current time); push a `DEPART` event for that (job, server) at `currentTime + serviceDuration`. * **DEPART(job, server)**: record the departure time (= current time); mark the server idle; then run dispatch. The simulation ends when the heap is empty. All jobs are guaranteed to eventually depart. ## Input format (scenario file) A UTF-8 text file. Tokens on a line are separated by one or more spaces. Blank lines are ignored. There are no comments. * Line 1: the literal word `servers` followed by an integer `N` (`N >= 1`). * Line 2: the literal word `discipline` followed by either `FIFO` or `SJF`. * Each remaining non-blank line describes one job as three tokens: `<jobId> <arrivalTime> <serviceDuration>` where `jobId` matches `[A-Za-z0-9_]+` and is unique, `arrivalTime` is an integer `>= 0`, and `serviceDuration` is an integer `>= 1`. The order in which jobs appear in the file is the **file order**, and it defines both the initial event sequence numbers and the order of the per-job section in the output. ## Output format (report file) Write exactly the following sections, in this order, one item per line. All event times and per-job metrics are integers (inputs are integers). Tokens on a line are separated by single spaces. Do not print anything else to the report. ``` TRANSCRIPT <one line per event, in the exact processing order> METRICS <one line per job, in file order> STATS mean_wait <value> max_queue <value> <one line per server, for server indices 0..N-1 in ascending order> ``` Event lines (one per event, in the order events are popped): * `t <time> ARRIVE <jobId>` * `t <time> START_SERVICE <jobId> server <serverIndex>` * `t <time> DEPART <jobId> server <serverIndex>` Per-job metric lines (file order), where `wait = serviceStartTime - arrivalTime` and `turnaround = departureTime - arrivalTime`: * `job <jobId> wait <wait> turnaround <turnaround>` Stats lines: * `mean_wait <x>`: the arithmetic mean of all jobs' wait times, formatted with exactly three digits after the decimal point, rounded half-up. * `max_queue <n>`: the maximum number of jobs simultaneously waiting in the queue (jobs that have arrived but not yet started service) observed at any instant during the run. * `server <i> utilization <x>`: for each server `i`, its busy time divided by the simulation end time, formatted with exactly three digits after the decimal point, rounded half-up. Busy time is the sum of `(departureTime - serviceStartTime)` over the jobs that server served. The simulation end time is the time of the last `DEPART`. A server that never serves a job has utilization `0.000`. ## Implementation Hints * Project path: `/home/user/project`. * Provide an executable entrypoint at the project root so that running `bash run.sh --scenario <scenarioPath> --out <outPath>` (from `/home/user/project`) runs the simulation and writes the report to `<outPath>`, creating parent directories for `<outPath>` if needed. The command must exit with status 0 on success. * The simulation MUST run inside a libGDX `HeadlessApplication` and MUST be driven by its render/tick loop; do not make any OpenGL/GL calls. * Events MUST be scheduled and ordered using libGDX's `com.badlogic.gdx.utils.BinaryHeap`. * Pin libGDX to version `1.14.2`. The environment has no internet access at run time; a local Gradle and a pre-populated dependency cache for the pinned libGDX artifacts are available, so resolve dependencies offline. * The report must be byte-for-byte deterministic across runs for the same input. Trailing whitespace on any line is not allowed.
