# Kanban Board with Fractional Ordering (Wasp)

## Background
Build a full-stack Kanban board application with the Wasp framework using the TypeScript spec (`main.wasp.ts`, `wasp: { version: "^0.24.0" }`). The board is made of columns (statuses) and cards. Cards can be moved within a column and across columns. Ordering is stored as a fractional floating-point `position`, so moving a card only ever updates that single card's `position` and never renumbers its siblings.

The app uses username & password authentication, a SQLite database (the Wasp development default), Prisma for the data model, and Wasp Operations for the API. All board data is private to the authenticated user who owns it.

## Requirements
- Data model (`schema.prisma`):
  - `Column`: `id` (Int, primary key), `title` (String), `position` (Float), and an owner relation to `User`.
  - `Card`: `id` (Int, primary key), `title` (String), `position` (Float), a relation to its `Column` exposed through a `columnId` (Int) foreign key, and an owner relation to `User`.
  - The `User` entity required by Wasp auth.
- Enable username & password authentication. Every operation below must act only on data owned by the currently authenticated user.
- Implement the following Wasp Operations. The operation names must match exactly (Wasp derives the HTTP route from the name):
  - Query `getBoard`
  - Action `createColumn`
  - Action `createCard`
  - Action `moveCard`
- Provide a root route `/` that renders an authenticated page displaying the board and performing an optimistic move (see the optimistic-update requirement below).

## Implementation Hints
- Project path: /home/user/kanban
- Start command (run from the project path): `wasp start`
- The Wasp server listens on port 3001; the web client listens on port 3000.
- Wasp exposes every Operation as an HTTP `POST` endpoint on the server at `/operations/<kebab-case-operation-name>`. Authenticated calls send an `Authorization: Bearer <sessionId>` header. The relevant endpoints are therefore:
  - `POST http://localhost:3001/operations/get-board`
  - `POST http://localhost:3001/operations/create-column`
  - `POST http://localhost:3001/operations/create-card`
  - `POST http://localhost:3001/operations/move-card`
- Username authentication endpoints (no session required): `POST http://localhost:3001/auth/username/signup` and `POST http://localhost:3001/auth/username/login`, each accepting a JSON body `{ "username": string, "password": string }`; a successful login responds with a JSON body containing a `sessionId` string.
- Any of the four operations invoked without a valid session must fail with `HttpError` status `401`.
- `getBoard` (no payload) returns the current user's board as a JSON array of column objects ordered by `position` ascending. Each column object must contain at least the keys `id`, `title`, `position`, and `cards`, where `cards` is an array of that column's cards ordered by `position` ascending. Each card object must contain at least the keys `id`, `title`, `position`, and `columnId`.
- `createColumn` (payload keys: `title` string, `position` number) creates a column owned by the current user at the given position and returns the created column object including `id`, `title`, `position`.
- `createCard` (payload keys: `title` string, `columnId` number, `position` number) creates a card with the given title and position inside the column identified by `columnId`, and returns the created card object including `id`, `title`, `position`, `columnId`. If `columnId` does not identify a column owned by the current user, the call must fail with `HttpError` status `403` or `404`.
- `moveCard` (payload keys: `cardId` number, `targetColumnId` number, `afterCardId` number optional, `beforeCardId` number optional) moves the card identified by `cardId` into the column identified by `targetColumnId` and assigns it a new fractional `position` according to the rules below. It updates only the moved card: the card's `columnId` becomes `targetColumnId` and its `position` is recomputed. No other card's `position` may change. It returns the updated card object including `id`, `title`, `position`, `columnId`. `moveCard` does not accept a caller-supplied position; the server computes it.
  - `afterCardId`, when provided, identifies the card that must end up immediately before the moved card (i.e. with a strictly smaller `position`).
  - `beforeCardId`, when provided, identifies the card that must end up immediately after the moved card (i.e. with a strictly larger `position`).
  - When both `afterCardId` and `beforeCardId` are provided, the moved card's new `position` must equal exactly the arithmetic mean of those two neighbors' `position` values.
  - When only `afterCardId` is provided, the moved card is placed at the tail of the target column: its new `position` must be strictly greater than that neighbor's `position`.
  - When only `beforeCardId` is provided, the moved card is placed at the head of the target column: its new `position` must be strictly smaller than that neighbor's `position`.
  - When neither neighbor is provided, the moved card is the only ordering reference in the target column and may take any valid `position`.
  - `cardId` and `targetColumnId` must identify a card and a column owned by the current user. `afterCardId` and `beforeCardId`, when provided, must identify cards that currently belong to the target column and are owned by the current user. Any violation (a missing resource, or a resource owned by another user) must fail with `HttpError` status `403` or `404`.
- The authenticated page at `/` must move a card optimistically: when a move is triggered from the UI, the cached result of the `getBoard` query must be updated to reflect the card's new column and ordering before the server confirms the change, using Wasp's client-side action optimistic-update mechanism for the `moveCard` action.
