# Fighting-Game Combo Detector on the libGDX Headless Backend ## Background You are building a deterministic, replay-driven input pipeline for a 2D fighting game on top of **libGDX 1.14.2** running under the **headless backend** (`com.badlogicgames.gdx:gdx-backend-headless:1.14.2`). There is no window and no OpenGL context. A recorded keystroke timeline is read from a text file, injected into the running application through a scripted input source, fanned out to several `InputProcessor`s via an `InputMultiplexer`, and a combo recognizer reports which special moves were performed. The application must boot a real `com.badlogic.gdx.backends.headless.HeadlessApplication`. All input must originate from a subclass of `com.badlogic.gdx.backends.headless.mock.input.MockInput` that replays the recorded timeline (the stock `MockInput` does nothing on its own). Events must be delivered to an `com.badlogic.gdx.InputMultiplexer` whose child processors honor libGDX consumption semantics: a processor that returns `true` from an event callback consumes the event so processors later in the chain never receive it. ## Requirements * Boot the game as a headless libGDX application; do not initialize any graphics/audio/OpenGL. * Replay a per-tick keystroke timeline from a text file through a `MockInput` subclass. * Dispatch every replayed key event through a single `InputMultiplexer` that chains, in this exact priority order, a `PauseProcessor` followed by a `ComboProcessor`. * The `PauseProcessor` must be able to pause/unpause and, while paused, swallow gameplay input so the `ComboProcessor` never sees it (correct multiplexer short-circuiting). * The `ComboProcessor` must recognize a fixed set of directional-motion + button combos within a bounded tick window, emit a chronological log of recognized combos, and produce a final tally. * Write the results to an output file. ## Implementation Hints * Project path: `/home/user/combo-detector` * Use libGDX `1.14.2` with the headless backend. The project is a Gradle multi-module build; the runnable module MUST be named `headless` and be launchable with the Gradle Application plugin. * Run command (rerunnable): `./gradlew --no-daemon headless:run --args="<input_file> <output_file>"` * `args[0]` = path to the input timeline text file; `args[1]` = path to the output file to (over)write. Absolute paths will be provided; use them as given. * The process MUST NOT exit until the output file has been fully written. ### Input timeline grammar * UTF-8 text. Each line is exactly one game tick; the tick index equals the 0-based line number. * A blank (or whitespace-only) line is a tick with no input events. * Otherwise a line is a whitespace-separated list of event tokens processed strictly left-to-right. Each token is a sign character immediately followed by a key name: * `+NAME` → that key is pressed this tick (dispatch a key-down for `NAME`). * `-NAME` → that key is released this tick (dispatch a key-up for `NAME`). * Every event token MUST be dispatched individually into the `InputMultiplexer` (as the multiplexer's `keyDown`/`keyUp`), so consumption semantics apply per event. * A trailing newline at end of file does not create an extra tick. * Key names map to `com.badlogic.gdx.Input.Keys` constants exactly as follows: `UP`→`Keys.UP`, `DOWN`→`Keys.DOWN`, `LEFT`→`Keys.LEFT`, `RIGHT`→`Keys.RIGHT`, `PUNCH`→`Keys.X`, `KICK`→`Keys.Z`, `PAUSE`→`Keys.P`. `UP`/`DOWN`/`LEFT`/`RIGHT` are directional keys; `PUNCH`/`KICK` are buttons; `PAUSE` is the pause key. ### PauseProcessor (first in the multiplexer) * Maintains a boolean paused state, initially `false`. * On a key-down of `PAUSE`: toggle the paused state and consume the event (return `true`). * On a key-up of `PAUSE`: consume the event (return `true`); do not change the paused state. * For any other key event (down or up): if currently paused, consume it (return `true`); if not paused, do not consume it (return `false`) so it reaches the `ComboProcessor`. ### ComboProcessor (second in the multiplexer) — direction model * Track the set of currently-held directional keys from the key-down/key-up events it actually receives. * Whenever it receives a directional key event, compute the current direction using numpad notation over the held horizontal/vertical components: `UP`=8, `DOWN`=2, `LEFT`=4, `RIGHT`=6, neutral=5, and diagonals combine (`DOWN`+`RIGHT`=3, `DOWN`+`LEFT`=1, `UP`+`RIGHT`=9, `UP`+`LEFT`=7). If `LEFT` and `RIGHT` are both held they cancel to horizontally-centered; if `UP` and `DOWN` are both held they cancel to vertically-centered. * Maintain `lastDirection`, initialized to `5` (neutral). On each directional event, recompute the direction `d`; if `d != lastDirection` and `d != 5`, append a direction token `(d, currentTick)` to a buffer; then set `lastDirection = d` regardless (including transitions to neutral, which record no token). * Direction events never consume (return `false`). ### ComboProcessor — combo recognition * Window `W = 12` ticks. * Defined combos, checked in this priority order: 1. `HADOKEN` — button `PUNCH` — motion `[2, 3, 6]` 2. `SHORYUKEN` — button `PUNCH` — motion `[6, 2, 3]` 3. `TATSU` — button `KICK` — motion `[2, 1, 4]` * On a button key-down that reaches the `ComboProcessor` at tick `T`: let `B` be the direction tokens whose tick `t` satisfies `T - t <= W`, in recording order. For each combo whose button matches the pressed button, in the priority order above, the combo is recognized iff the last `k` tokens of `B` (where `k` is that combo's motion length) equal the combo's motion in order. Recognize at most one combo per button press (the first match in priority order). * On recognition: append one output record for tick `T` with the combo name, increment that combo's tally, and clear the entire direction-token buffer. * A button press that recognizes a combo consumes the event (return `true`); any other button event returns `false`. Button events never record direction tokens and never change `lastDirection`. ### Output file format * First, one line per recognized combo, in chronological order of the tick at which it was recognized: `TICK  <NAME>` (single spaces; `<tick>` is the decimal tick index). * Then a line containing exactly `--- TALLY ---`. * Then exactly three tally lines, in combo priority order: `HADOKEN <count>`, `SHORYUKEN <count>`, `TATSU <count>`. * Then a final line `TOTAL <n>` where `<n>` is the total number of recognized combos. * Lines are separated by `\n`; a trailing newline is allowed.
