An order's `status` must behave as a strict finite state machine (FSM): only a fixed set of transitions is ever allowed, illegal transitions must be rejected without side effects, and every accepted transition must be permanently recorded in an append-only audit trail. Correctness must hold even when many processes try to advance the same order at the same time. Use **Sequelize v6** with a file-based **SQLite** database. Implemented the order-lifecycle FSM CLI at /home/user/project:

- **transitions.js** — the single, frozen, data-driven transition table (`{status: [allowed next statuses]}`) that both the CLI and the transition/legality checks consult. `isLegalTransition(from, to)` is the only place legality is decided — no ad-hoc per-call conditionals.
- **db.js** — Sequelize v6 + SQLite setup. `ensureSchema()` runs `CREATE TABLE IF NOT EXISTS` for `Orders` and `OrderStatusHistories` (plus an index on `orderId`), so every subcommand can safely create-or-reuse the schema on the given `--db` file. `configureConnection()` sets `PRAGMA busy_timeout` as a defense-in-depth measure.
- **orderService.js** — `createOrder`, `transitionOrder`, `getOrderWithHistory`. `transitionOrder` runs inside a Sequelize **`IMMEDIATE`** sqlite transaction (`Transaction.TYPES.IMMEDIATE`), which acquires SQLite's write lock at `BEGIN` time rather than lazily. Since SQLite only ever allows one writer, this fully serializes the read-status → check-legality → write-status+history critical section across all processes/connections touching the same db file, making the whole operation atomic and race-free. Illegal/not-found outcomes are returned without throwing and without performing any write, so status and history are left untouched. A small busy-retry wrapper (`withBusyRetry`) transparently retries on transient `SQLITE_BUSY`/`SQLITE_LOCKED` errors.
- **cli.js** — parses `--db/--id/--to`, ensures schema on every invocation, and implements `init`, `create`, `transition`, `show`, `transitions` exactly per the required stdout JSON shapes and exit codes (0 success, 3 illegal transition, 4 not found). `show`'s history is ordered by `at` then `id` ascending to guarantee correct chronological order even when timestamps collide.
