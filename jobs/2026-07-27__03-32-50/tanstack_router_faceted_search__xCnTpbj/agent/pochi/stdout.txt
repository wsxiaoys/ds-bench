# URL-Driven Faceted Product Search (TanStack Start + TanStack Router) ## Background Build an e-commerce faceted product search where the **URL is the single source of truth** for all filter state. The app is a TanStack Start application (React) using TanStack Router's typed, validated search params. Every filter is deep-linkable and shareable: opening a URL cold must render exactly the filtered/sorted/paginated results that URL describes, and browser back/forward must restore prior filter states. Use `@tanstack/react-start` and `@tanstack/react-router` (install the current stable release) together with `zod` for search-param validation. Product data must live in a **local SQLite database** seeded from the catalog file provided in the environment. There are **no external services**; everything runs locally. ## Requirements * A single search page (the app's index route `/`) that lists products from SQLite and exposes faceted filtering entirely through validated URL search params. * All of the following filter state MUST be represented in the URL search params (these exact names) and validated with Zod so that any missing, malformed, or out-of-range value is coerced to its default instead of throwing: * `q`: full-text query (string). Matches case-insensitively as a substring against the product **name OR description**. Default `""` (matches everything). * `categories`: multi-select array of category slugs. When non-empty, a product matches only if its category is in the set. Default `[]` (all categories). * `minPrice`: number, inclusive lower bound on price. Default `0`. * `maxPrice`: number, inclusive upper bound on price. Default `1000000`. * `inStock`: boolean. When `true`, only in-stock products are shown; when `false`, stock is ignored. Default `false`. * `sort`: one of exactly `name_asc`, `price_asc`, `price_desc`, `rating_desc`. Default `name_asc`. * `page`: 1-based page number (integer >= 1). Default `1`. * Page size is fixed at **6** products per page. * The **route loader performs all filtering, sorting, and pagination on the server** against the SQLite database, driven by the parsed search params. The browser must NOT receive the full catalog and filter client-side: a cold HTTP request for a filtered URL must return HTML containing only that page's matching products (server-rendered), not the non-matching ones. * **Category facet counts**: next to each category the UI shows how many products would match. A category's facet count reflects all currently-active filters (`q`, `minPrice`, `maxPrice`, `inStock`) **EXCEPT the `categories` selection itself** (standard faceted behavior, so a user can widen the category selection). Counts update as the other filters change. * Changing any filter through the UI updates the URL search params (the URL is authoritative, not component state). Browser back/forward navigation restores the exact prior filter state and its rendered results. ## Implementation Hints * Project path: /home/user/faceted-search * Start command: `npm run dev` * Port: 47615 (the dev server MUST listen on http://localhost:47615). Do not use any other port. * Seed the SQLite database from the catalog provided at `/home/user/faceted-search/seed/products.json` (20 products). Each seed record has the keys: `id` (int), `name` (string), `description` (string), `category` (one of `electronics`, `books`, `clothing`, `home`, `toys`), `price` (number, USD), `inStock` (boolean), `rating` (number), `createdAt` (ISO date string). Category slugs used in `categories` search params are exactly those five lowercase strings. * Sorting semantics: `name_asc` = ascending by `name`; `price_asc`/`price_desc` = by `price`; `rating_desc` = descending by `rating`. * The rendered page MUST expose these stable hooks so the behavior is testable (exact `data-testid` values): * `search-input`: the text input bound to `q`. It is inside a form; submitting the form (Enter) commits `q` to the URL. * `facet-category-<slug>`: a clickable control that toggles that category in `categories` (e.g. `facet-category-electronics`). Clicking it re-filters immediately. * `facet-count-<slug>`: an element whose text content is the numeric facet count for that category (e.g. `facet-count-electronics`). * `filter-instock`: a control that toggles the `inStock` filter. * `filter-min-price` and `filter-max-price`: numeric inputs bound to `minPrice`/`maxPrice`, committed on change. * `sort-select`: a `<select>` whose option values are exactly the four allowed `sort` values. * `results-total`: an element whose text content contains the total number of products matching the current filters (across all pages, not just the current page). * `product-card`: one per product shown on the current page; each contains a descendant with `data-testid="product-name"` whose text is the product name. * `page-next` and `page-prev`: pagination controls that move `page`; `page-current` shows the current page number. * Invalid/malformed search params (e.g. `page=abc`, `minPrice=-5`, `maxPrice=notanumber`, `sort=bogus`, an unknown category) MUST be coerced to their defaults and the page must still render normally with HTTP 200.
