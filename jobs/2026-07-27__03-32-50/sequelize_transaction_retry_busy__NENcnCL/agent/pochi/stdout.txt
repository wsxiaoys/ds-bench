# Resilient SQLite Transaction Runner with Sequelize ## Background A Node.js service uses **Sequelize 6 (v6.37.x)** on top of a single **SQLite** database file. Many operations run in parallel and all mutate one shared counter row. Because SQLite allows only a single writer at a time, naive parallel writers either lose updates or crash with transient lock-contention errors. Your job is to build a transaction runner that stays correct and durable under heavy concurrency. ## Requirements Build a small project that exposes a reusable transaction helper and a command-line driver. * A `withRetry` helper runs a unit of work inside a database transaction and automatically retries it, using **exponential backoff** with a **capped maximum number of attempts**, but **only** when the failure is a transient SQLite lock-contention error (the kind SQLite raises while the database is momentarily busy/locked). Any other error must be surfaced to the caller **immediately, without any retry**. * When every attempt keeps hitting lock contention and the attempt cap is reached, `withRetry` gives up and throws an error that clearly signals the retries were exhausted. * An increment operation atomically raises a shared counter by exactly one, based on the value it reads, and records an audit trail of what it saw and what it wrote. It must be safe to run many of these concurrently with **no lost updates**: the final counter value must equal the number of increments that succeeded, and the audit trail must show that every increment observed a distinct, previously-unseen counter value. * The SQLite connection must be configured so the system can actually sustain concurrent writers rather than immediately failing. ## Implementation Hints * Project path: `/home/user/project` * The project must be a CommonJS Node.js project.
