## What it does

**Configuration** — All settings read from env vars with the specified defaults: `REDIS_HOST` (127.0.0.1), `REDIS_PORT` (6379), `STREAM_KEY`, `GROUP_NAME`, `CONSUMER_NAME`, `LANCEDB_DIR`, `TABLE_NAME`, `BATCH_SIZE` (50), `VECTOR_DIM` (32).

**Consumer group setup** — `ensure_group()` calls `XGROUP CREATE ... MKSTREAM` (id `0` so a fresh group drains all existing entries), ignoring `BUSYGROUP` on reruns.

**Crash recovery (reclaim phase)** — `reclaim_pending()` uses `XAUTOCLAIM` starting from `0-0` with `min_idle_time=0`, looping through the cursor until the PEL is drained. A just-crashed batch is picked up immediately. Each claimed batch is committed to LanceDB before `XACK`, giving at-least-once delivery.

**Drain phase** — `drain_new()` reads new entries via non-blocking `XREADGROUP` with `>`, batched by `BATCH_SIZE`, committing each batch to LanceDB before acknowledging. When a read returns nothing, the stream is drained and the loop exits.

**Exactly-once effect** — `upsert_rows()` uses LanceDB `merge_insert("id").when_matched_update_all().when_not_matched_insert_all()`, so a re-delivered message overwrites its row instead of duplicating. Vectors are decoded with `numpy.frombuffer(raw, dtype='<f4')` and stored in a fixed-size `float32` list column of length `VECTOR_DIM`.

**Output** — Prints exactly `DONE ingested=<int> reclaimed=<int>` where `ingested` is the total committed this run (new + reclaimed) and `reclaimed` is the count of recovered pending entries, then exits with status 0.
