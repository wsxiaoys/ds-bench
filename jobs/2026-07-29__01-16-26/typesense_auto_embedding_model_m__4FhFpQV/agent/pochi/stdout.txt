### Migration Strategy & Implementation Details

To migrate the vector field dimensions without dropping or recreating the collection (and without incurring validation conflicts due to mismatched dimensions), the following sequence of operations was executed:

1. **Schema Alteration (Drop Field)**:
   We temporarily removed the `content_embedding` field from the `notes` collection schema via a `PATCH /collections/notes` call. 
   *Note: Dropping a field in Typesense only updates the schema and the in-memory index; it does not delete the underlying document data on disk.*

2. **In-place Document Updates**:
   With `content_embedding` temporarily omitted from the schema, Typesense accepts any arbitrary structure for this unmapped field. We used the bulk import endpoint with `action=update` to overwrite the existing 4-dimensional vectors with the pre-generated 8-dimensional vectors from `/home/user/migration/new_vectors.jsonl`.

3. **Schema Alteration (Add Field back with 8 Dimensions)**:
   We added the `content_embedding` field back to the schema with `type: float[]` and `num_dim: 8`. During this schema addition, Typesense scanned and validated the existing documents on disk. Since all documents had already been updated to the 8-dimensional vectors in Step 2, the validation passed seamlessly, and Typesense rebuilt the HNSW index for the 8-dimensional vector space.

4. **Validation**:
   We verified that the collection continues to exist as `notes`, contains all original documents with their original non-vector properties, and successfully performs nearest-neighbor vector search queries against the new 8-dimensional field.
