## Design decisions

### Drain-only loop
Uses `stream.try_next()` (non-blocking) in a tight `while True` loop. Returns `None` immediately when no further events are buffered, so the process exits without blocking.

### Event → LanceDB mapping
| MongoDB `operationType` | LanceDB operation |
|---|---|
| `insert` | `upsert_row()` via `merge_insert("id")` |
| `update` | `upsert_row()` via `merge_insert("id")` — change stream opened with `full_document="updateLookup"` so the complete post-update document is always available |
| `replace` | `upsert_row()` via `merge_insert("id")` |
| `delete` | `delete_row()` via `table.delete("id = '<id>'")`  |

Each event is applied **immediately and individually** (not batched), which correctly handles sequences like `insert → update → delete` of the same id within one run — the net result is no row in LanceDB.

### Embedding
```python
digest = hashlib.sha256(text.encode("utf-8")).digest()
vector = [digest[i] / 255.0 for i in range(8)]  # stored as float32
```
Exactly the specified formula: SHA-256 digest → first 8 bytes → divide by 255.0 → 8-dim `float32` vector.

### Schema
```
id       string
text     string
category string
vector   fixed_size_list<float32>[8]
```

### Resume token
- **On startup**: if `resume_token.json` exists and is non-empty, the change stream is opened with `resume_after=<token>` — no events are missed or duplicated.
- **During the run**: `last_token` is updated from `stream.resume_token` after every event, so the token always reflects the last processed position.
- **On exit**: the final token is persisted to `resume_token.json` even when zero events were processed (the cursor reports the current cluster time), preventing replay of events that occurred between runs.

### Idempotency
Re-running with no new events leaves the LanceDB table completely unchanged and writes only an updated resume token — no errors.

### Verified test scenarios
1. Cold start (no prior token, no events) → token created, table empty ✓  
2. Insert + update + delete across two runs → correct upsert and tombstone ✓  
3. `replace` operation → treated identically to `insert`/`update` ✓  
4. Insert → update → delete of the same id **within one run** → no net row ✓  
5. Idempotent re-run with no new events → table unchanged ✓  
6. Crash recovery via saved token → no missed events across runs ✓
