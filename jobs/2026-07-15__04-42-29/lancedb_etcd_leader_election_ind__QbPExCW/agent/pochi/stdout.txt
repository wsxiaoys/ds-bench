## Architecture

### Election protocol (etcd v3 HTTP/JSON gateway, `requests` only)

```
acquire()
  1. POST /v3/lease/grant  → lease_id  (TTL seconds)
  2. POST /v3/kv/txn       → atomic compare-and-create
       compare: create_revision == 0   (key absent)
       success: PUT election_key=worker_id LEASE=lease_id
  3. On TXN success → read back create_revision → fencing token
     On TXN failure → revoke lease immediately (no leak)
  4. Start daemon keepalive thread (fires every TTL/2 s)
```

### Fencing token
The election key's **`create_revision`** from etcd is used directly as the fencing token. Because etcd's global revision counter only ever increases, every new leadership term gets a strictly larger token automatically — no extra counter is needed.

### run_maintenance() fencing (double-check pattern)
```
1. assert is_leader locally (fast path)
2. GET election_key from etcd → verify create_revision == our token
                              → verify lease binding matches ours
3. snapshot version_before + unindexed_before
4. GET election_key again (guard against TOCTOU)
5. tbl.optimize()  ← compacts fragments + merges delta index
6. snapshot version_after + unindexed_after
```
A stale leader (whose lease expired) will get `PermissionError` at step 2 because the key is either gone or owned by a new term.

### Failover modes

| Mode | Mechanism |
|---|---|
| **Graceful** (`resign()`) | Stop keepalive → DELETE key → revoke lease; follower wins TXN instantly |
| **Crash** (`simulate_crash()`) | Stop keepalive thread only; etcd expires the lease after TTL, garbage-collecting the key; follower wins after TTL |
