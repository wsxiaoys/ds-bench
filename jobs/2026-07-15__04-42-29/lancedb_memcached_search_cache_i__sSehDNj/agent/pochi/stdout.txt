### Architecture

#### Cache key (`_build_cache_key`)
A SHA-256 digest over five length-prefixed fields:
```
table_name | version | k | filter (or "") | query_vector as float32 bytes
```
Length-prefixing (4-byte big-endian) prevents any two distinct inputs from producing the same byte sequence. The resulting key is always `ldb_cache:<64-hex-chars>` — well within memcached's 250-byte limit.

#### Version counter (`ldb_ver:<table_name>`)
A single memcached integer key, shared across all processes pointing at the same table:
- **`__init__`** calls `mc.add(...)` — a no-op if the key already exists, so concurrent initialisation is safe.
- **`add` / `update`** call `mc.incr(...)` after the LanceDB write succeeds. Because the version is part of every cache key, bumping it makes **all** previously cached entries unreachable (they still occupy memory until TTL expires, but can never be hit again).
- **Cross-instance invalidation** works automatically: a writer on instance A increments the counter; instance B reads the new version before building its cache key, so it always sees a miss for stale data.

#### Fresh reads on cache miss
The table is re-opened with `db.open_table(table_name)` on every miss rather than reusing a long-lived handle. This ensures the query targets the latest committed state even if another process wrote rows after `__init__` was called.

#### Result schema
Each result dict has exactly `{"id": int, "category": str, "_distance": float}`, sorted by ascending `_distance`. Cache stores `json.dumps(results).encode()` so hit and miss return byte-for-byte identical Python objects.

#### TTL
Passed directly to `mc.set(..., expire=ttl_seconds)`. Even without a version bump, cached entries expire on their own after the configured TTL.
