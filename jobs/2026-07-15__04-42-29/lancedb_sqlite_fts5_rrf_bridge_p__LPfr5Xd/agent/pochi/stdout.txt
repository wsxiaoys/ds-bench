## Architecture

```
search(query, query_vector, k, keyword_weight, title_weight, body_weight)
       │                │
       ▼                ▼
_keyword_candidates   _vector_candidates
  SQLite FTS5            LanceDB
  bm25() ORDER BY        .search().distance_type()
  (more-neg = better)    .limit(pool)
       │                │
       └──────┬──────────┘
              ▼
        _weighted_rrf
   fused_score(d) =
     kw_w  * 1/(rrf_k + bm25_rank(d))
   + (1-kw_w) * 1/(rrf_k + vec_rank(d))
   sort: score DESC, id ASC
              ▼
        top-k list[dict{id,score}]
```

## Key design decisions

| Concern | Choice |
|---|---|
| Config | Read once at import time from `/app/data/config.json`; `table_name`, `rrf_k`, `distance_metric` never hard-coded |
| Candidate pool | `max(50, k)` — always at least 50 from each store |
| BM25 ordering | `ORDER BY bm25(table, title_w, body_w), rowid` — tie-break by rowid inside SQLite so the pool itself is stable |
| Vector ordering | Sort by `(_distance, id)` after LanceDB returns results — deterministic even if LanceDB returns ties |
| RRF ranks | 1-based; absent-store contribution = 0 (not penalised) |
| Tie-breaking | `(-score, id)` sort key → fully deterministic across identical calls |
| Return length | `min(k, len(all_candidates))` — never raises on small corpora |
