### Architecture / design decisions

#### Two-phase startup

| Phase | Redis call | Purpose |
|-------|-----------|---------|
| **Recover** | `XAUTOCLAIM … start_id=0-0 min_idle_time=0` | Sweep the full PEL and re-own every un-acked entry from *any* prior consumer (including a crashed one). Iterates with the returned cursor until `0-0` signals exhaustion. |
| **Consume** | `XREADGROUP … ">"` | Deliver new, never-before-seen entries in `BATCH_SIZE` chunks until the stream is empty (`None` / `[]` response). `block=None` keeps the call non-blocking. |

#### Exactly-once effect in LanceDB
Redis delivers at-least-once (un-acked = re-delivered). Idempotency is enforced at the LanceDB layer with a **merge-insert keyed on the business `id`**:

```python
table.merge_insert("id")
     .when_matched_update_all()      # overwrite existing row
     .when_not_matched_insert_all()  # insert new row
     .execute(batch)
```

A re-processed batch overwrites its rows in place — row count never grows from duplicates.

#### ACK ordering (crash-safe)
```
_upsert_batch(table, rows)           # 1. durable LanceDB commit
r.xack(STREAM_KEY, GROUP_NAME, *ids) # 2. only then remove from PEL
```
A crash between steps 1 and 2 leaves messages in the PEL; the recovery phase picks them up on the next run. The merge-insert makes re-applying them a no-op from the data perspective.

#### Key implementation details
- `redis.Redis` is created **without** `decode_responses=True` so the binary `vector` field survives the round-trip intact; text fields are explicitly `.decode("utf-8")`.
- The vector is decoded with `numpy.frombuffer(raw, dtype="<f4")` and stored as a typed `pa.list_(pa.float32(), VECTOR_DIM)` column — the LanceDB schema is declared once at module level and reused for every batch write.
- The `BUSYGROUP` error from `XGROUP CREATE` is swallowed silently; any other `ResponseError` propagates.
- The `MKSTREAM` flag means the consumer can start before any producer has written a single message (test 4 demonstrates this).
