# Toast Notification Queue Manager (Capacitor Toast, Web) ## Background The `@capacitor/toast` plugin exposes a single fire-and-forget `Toast.show(...)` method. On the **web** implementation, calling `Toast.show(...)` immediately appends a `<pwa-toast>` element to `document.body` and resolves right away — it does **not** wait for the toast to finish, does **not** remove the element, and gives no way to prevent multiple toasts from piling up on top of each other. Your job is to build a **toast queue manager** on top of the Capacitor Toast web plugin that serializes many `show` calls so that toasts are displayed strictly one after another (never overlapping), with configurable per-toast display duration and screen position, plus an API to enqueue toasts and to await the queue draining completely. The manager must behave deterministically even when a large burst of `enqueue` calls arrives synchronously. ## Requirements * Build a small web app that imports the real `@capacitor/toast` plugin and uses its **web implementation** (no native platform is available). * Implement a queue manager that: * Displays queued toasts strictly sequentially in FIFO (enqueue) order — never more than one toast element present at the same time. * Uses the real `Toast.show(...)` API to create each toast (so a `<pwa-toast>` element is appended to `document.body` for every displayed toast). * Supports a configurable display duration and position per toast. * Removes each displayed `<pwa-toast>` element once its duration has elapsed, before starting the next toast. * Handles rapid synchronous bursts of enqueue calls deterministically and in order. * Expose the queue API on the global `window` object so it can be driven from the browser console / an automation script. ## Implementation Hints * Use a bundler (Vite is recommended) so the `@capacitor/toast` npm module can be imported and run in a plain browser. On web, `Toast.show(...)` resolves immediately after appending `<pwa-toast>`, so the manager itself owns the display timing and the element cleanup. * Because `Toast.show(...)` resolves before the toast is actually done, chain the queue with promises/timers so the next toast starts only after the current one's duration has fully elapsed and its element has been removed. * The Capacitor Toast `ShowOptions.duration` only accepts `'short'` (2000ms) or `'long'` (3500ms); your manager's own numeric duration controls the real sequencing/cleanup timing, independent of that coarse plugin value. * Project path: `/home/user/toast-queue` * Build command: `npm run build` * Start command: `npm run preview` (must serve the built app at `http://localhost:4173`) * Port: `4173` * The served page MUST attach the following API to `window`: * `window.enqueueToast(options)` — `options` is an object `{ text: string, duration?: number | 'short' | 'long', position?: 'top' | 'center' | 'bottom' }`. `duration` as a number is the display time in **milliseconds**; the string `'short'` maps to `2000` and `'long'` maps to `3500`; when omitted it defaults to `2000`. `position` defaults to `'bottom'`. It returns a `Promise<void>` that resolves ONLY after this specific toast has been displayed for its full duration AND its `<pwa-toast>` element has been removed. * `window.drainToastQueue()` — returns a `Promise<void>` that resolves when the queue is empty and no toast is currently active; if called while already idle it resolves immediately. * `window.getQueueState()` — returns synchronously an object `{ pending: number, active: boolean }`, where `pending` is the number of toasts waiting (not yet shown) and `active` is whether a toast is currently being displayed. * Observable display contract (these are the outcomes checked in a headless browser): * Every displayed toast is created via the real `Toast.show(...)`, so it appears as a `<pwa-toast>` element in `document.body`. Each such element MUST carry the toast text on its `text` property (as set by the plugin) and MUST have a `data-position` attribute equal to that toast's resolved position. * At no point may more than one `<pwa-toast>` element exist in the document at the same time. * `<pwa-toast>` elements must appear in the exact order the toasts were enqueued. * Each `<pwa-toast>` element must remain in the document for approximately its configured duration and then be removed before the next one appears.
