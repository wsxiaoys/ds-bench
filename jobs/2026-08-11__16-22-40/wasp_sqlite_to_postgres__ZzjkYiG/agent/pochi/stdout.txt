# Migrate a Wasp App from SQLite to PostgreSQL ## Background You are given an existing, working Wasp (wasp.sh) full-stack app called **TaskVault** that stores its data in the default **SQLite** database. SQLite is fine for early development, but the team now needs a production-grade database and a background job queue, so the app must be migrated to **PostgreSQL**. Wasp's built-in background job executor, **PgBoss**, only works on PostgreSQL, so once the migration is done you must also add a PgBoss background job to justify (and exercise) the new database. The project is a classic Wasp project: a `main.wasp` declaration file, a separate `schema.prisma` file that holds the datasource/models, a `migrations/` directory with the current SQLite migrations, and the React/Node source under `src/`. The app has a `Task` entity, a `getTasks` query, a `createTask` action, a page that lists and adds tasks, and a custom HTTP API endpoint `GET /api/stats`. ## Requirements * Switch the app's database from SQLite to PostgreSQL. * Point the app at the **local** PostgreSQL server that is already running in this environment. * Regenerate the database migrations so they are PostgreSQL migrations (the old SQLite migrations cannot be reused). * Keep the existing functionality working after the migration: the task list (query + action) and the `GET /api/stats` endpoint must still work. * Add a background **job** that uses the **PgBoss** executor and runs automatically, exactly once, every time the server starts. This is only possible because the app now runs on PostgreSQL. * The app must still build and run with `wasp start`. ## Implementation Hints * Project path: `/home/user/taskvault` * A local PostgreSQL server is already running in this environment and is reachable at: `postgresql://postgres:postgres@localhost:5432/taskvault` Configure the app to use it (Wasp reads the database connection string from the `DATABASE_URL` environment variable in the project's `.env.server` file). * To change the database backend you edit the `datasource` block's `provider` in `schema.prisma`; Wasp only supports `"sqlite"` or `"postgresql"`. * SQLite migrations are incompatible with PostgreSQL. Remove the existing `migrations/` directory (and clear Wasp's cached artifacts), then create a brand-new initial migration for PostgreSQL. After this, `migrations/migration_lock.toml` must report the `postgresql` provider. * Use Wasp's own database commands (`wasp db ...`) rather than calling `prisma` directly, so Wasp stays in sync. * Trigger the PgBoss job from the server setup function so it runs on every server start. * The background job must record its runs in the database. Add a new entity named `EventLog` to the data model with exactly the fields `id` (auto-increment primary key), `message` (a text/String column), and `createdAt` (a timestamp that defaults to now). This entity must be created by your new PostgreSQL migration. Each time the startup job runs it must insert exactly **one** new `EventLog` row. * The existing `GET /api/stats` endpoint must return HTTP 200 with a JSON body of the shape `{ "taskCount": <number> }`, where `<number>` is the current count of `Task` rows read from the database. * Start command: `wasp start` (the Wasp server listens on port `3001` and the web client on port `3000`).
