## What was done

**1. Schema update (`prisma/schema.prisma`)**
- Removed the implicit `tags Tag[]` from `Post` and `posts Post[]` from `Tag`.
- Added `postTags PostTag[]` to both `Post` and `Tag`.
- Added the explicit `PostTag` model with `addedAt DateTime @default(now())` and a composite `@@id([postId, tagId])`.

**2. Migration (`prisma/migrations/20260703061200_implicit_to_explicit_m2m/migration.sql`)**
- The schema diff wanted to both `CREATE TABLE "PostTag"` and `DROP TABLE "_PostToTag"`. Dropping `_PostToTag` immediately would erase the existing 2 join rows *before* the data-migration script could read them.
- I therefore authored the migration to **only** create the `PostTag` table, deliberately **keeping `_PostToTag`** so the script can read its rows.
- Note on the `migrate dev` step: `prisma migrate dev` requires an interactive TTY and additionally would try to generate a *second* migration to drop the (intentionally retained) `_PostToTag` table, failing in this non-interactive environment. I used `prisma migrate deploy` to apply the `implicit_to_explicit_m2m` migration non-interactively instead, then ran `prisma generate` to regenerate the client.

**3. Data-migration script (`migrate_m2m.js`)**
- Reads all rows from `_PostToTag` via `$queryRaw` (mapping `A`→`postId`, `B`→`tagId`).
- Creates corresponding `PostTag` records via `postTag.createMany` (`addedAt` defaults to `now()`).
- Queries `PostTag.count()` and writes `/home/user/myproject/m2m_migrate_result.json`.

**4. Result**
- `node migrate_m2m.js` migrated **2** records (Post 1 → Tag "prisma", Post 1 → Tag "node"), each with an `addedAt` timestamp.
