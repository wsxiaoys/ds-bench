## The Problem

The circular dependency was caused by each function file importing the typed `api` object from `_generated/api`:

```
a.ts → _generated/api.d.ts → a.ts (cycle!)
b.ts → _generated/api.d.ts → b.ts (cycle!)
c.ts → _generated/api.d.ts → c.ts (cycle!)
```

The generated `api.d.ts` uses `ApiFromModules<{ a: typeof a; b: typeof b; c: typeof c }>`, which creates deeply-nested mapped types that reference back into the importing files. This self-referential type structure triggered TypeScript errors:
- `TS7022`: `'funcA' implicitly has type 'any'` (referenced directly/indirectly in its own initializer)
- `TS2615`: circularly references itself in mapped type
- `TS2339`: Property does not exist on type (due to incomplete resolution)

## The Fix

Replaced the import of the strongly-typed `api` from `./_generated/api` with `anyApi` from `convex/server` in all three files (`a.ts`, `b.ts`, `c.ts`):

```typescript
import { query } from "./_generated/server";
import { anyApi } from "convex/server";

const api = anyApi;

export const funcA = query({
  args: {},
  handler: async (ctx: any) => {
    return ctx.runQuery(api.b.funcB);
  },
});
```

`anyApi` provides an untyped (`any`) API reference object that allows the same `api.b.funcB` / `api.c.funcC` / `api.a.funcA` call syntax at runtime, but does **not** pull in the generated type definitions that depend on the function files. This breaks the type-level import cycle entirely while keeping the runtime behavior identical.
