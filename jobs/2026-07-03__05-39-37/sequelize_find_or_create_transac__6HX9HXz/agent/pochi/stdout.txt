## What the module does

**Models:**
- `User` — `username` (STRING, unique), `status` (STRING)
- `AuditLog` — `action` (STRING), `username` (STRING)

**Hooks on `User`:**
- `beforeCreate` — creates an `AuditLog` entry with `action: 'Creating user'` and the user's `username`, passing `options.transaction` to `AuditLog.create` so the row joins the same transaction.
- `afterCreate` — throws `new Error('Simulated failure')` when `username` is exactly `'error_user'`.

**Exports:** `initDB`, `runFindOrCreate`, `User`, `AuditLog`.

## Key implementation detail — why a managed transaction is needed

Sequelize v6's `findOrCreate` creates an internal transaction, but it **commits** that transaction in a `finally` block even when an error is thrown during `create`:

```js
} finally {
  if (internalTransaction && transaction) {
    await transaction.commit();   // commits even on error!
  }
}
```

This means if we relied solely on the internal transaction, the `AuditLog` row written by `beforeCreate` would **survive** the `afterCreate` failure — the exact problem the task warns about.

The solution wraps the `findOrCreate` call in a **managed transaction** (`sequelize.transaction(async (t) => { ... })`):

1. We pass `transaction: t` to `findOrCreate`, so `internalTransaction` is `false` and the `finally` block does **not** commit.
2. When `afterCreate` throws, the error propagates out of the managed-transaction callback.
3. `sequelize.transaction` REDACTEDmatically **rolls back**, removing both the `User` row and the `AuditLog` row written by `beforeCreate`.
