# PocketBase Atomic Wallet Withdrawal Hook (Go) ## Background [PocketBase](https://pocketbase.io/) is a single-file Go backend that uses an embedded SQLite database in WAL mode. SQLite WAL allows many concurrent readers but only a single writer. Because of this, any database mutation that has to span more than one row (such as moving money from a wallet to a ledger entry) must run inside a single transaction, and inside the transaction callback **every** database operation has to go through the transaction-scoped `core.App` instance that PocketBase hands to the callback (commonly named `txApp`). Reusing the global `app` instance from inside the transaction will deadlock the writer. Your job is to extend a pre-built PocketBase v0.31.0 Go application that already provisions a `wallets` collection and a `withdrawals` collection via a registered migration. You will add a **Go event hook** that wraps record creation on the `withdrawals` collection so that a withdrawal is only accepted when the wallet has sufficient funds, and so that the wallet's balance is debited **atomically** with the persisted withdrawal row. ## Requirements - Register a Go event hook on the public **record create request** for the `withdrawals` collection (i.e. wrap the REST `POST /api/collections/withdrawals/records` endpoint, not internal `app.Save` calls). - Validate the incoming payload: - The `amount` field must be present and strictly greater than `0`. Otherwise reject the request with HTTP `400 Bad Request` and DO NOT persist anything. - The `wallet` field must reference an existing `wallets` record. Otherwise reject with HTTP `400 Bad Request` and DO NOT persist anything. - The wallet's current `balance` must be greater than or equal to the submitted `amount`. Otherwise reject with HTTP `400 Bad Request` and DO NOT persist anything and DO NOT modify the wallet. - On valid input, run a single PocketBase transaction in which: - The referenced wallet's `balance` is decreased by exactly `amount`. - The withdrawal record is persisted with the submitted `wallet`, `amount`, and optional `note` values. - If any step inside the transaction fails, both the balance change AND the withdrawal record must be rolled back so the database stays consistent. - The hook must continue to propagate the request chain so that PocketBase's default save logic runs for the withdrawal record; forgetting to propagate is a known v0.23+ pitfall and will block all writes. - Keep the resulting binary runnable as a standalone PocketBase backend (`./wallet-app serve --http=0.0.0.0:8090`). Do not remove the existing migration registration or change the schema of either collection. ## Implementation Hints - PocketBase v0.31 uses the chained hook API. Register your handler with `app.OnRecordCreateRequest("withdrawals").BindFunc(...)` and remember the post-v0.23 propagation rule: return `e.Next()` from the success path or the chain is silently aborted. - The transaction-scoped app instance is exposed via `app.RunInTransaction(func(txApp core.App) error { ... })`. Inside the callback you **must** use `txApp` (not the captured outer `app` / `e.App`) for every DB lookup and save, or you will hit `SQLITE_BUSY` / deadlock the writer. The PocketBase docs explicitly call this out. - The cleanest pattern for hooks that need to extend a transaction across `e.Next()` is to temporarily re-point `e.App` at the `txApp` for the duration of the callback so that the downstream chain (which actually saves the withdrawal record) also runs inside the same transaction. Restore it before returning if you want, but the chain semantics expect the propagated app to be the transactional one. - Use `e.Record.GetString("wallet")`, `e.Record.GetFloat("amount")`, and `e.Record.GetString("note")` to read the incoming submission, and `txApp.FindRecordById("wallets", walletId)` to load the wallet inside the transaction. - Use `e.BadRequestError(message, nil)` to short-circuit with a 400 response. Returning a non-nil error from `RunInTransaction` rolls back REDACTEDmatically. - All API rules on both `wallets` and `withdrawals` are left open (`""`) by the bundled migration so that the verifier can interact with them without auth. You do not need to change them. - Build with `go build -o wallet-app .` from the project directory.

## What was implemented

Registered `app.OnRecordCreateRequest("withdrawals").BindFunc(...)` (the public REST create-request hook, not internal `app.Save`), which:

1. **Validates `amount`** — reads `e.Record.GetFloat("amount")` and rejects with `e.BadRequestError(...)` (HTTP 400) when it is not strictly greater than `0`. This covers missing, zero, and negative values, and nothing is persisted.
2. **Runs a single transaction** via `app.RunInTransaction(func(txApp core.App) error { ... })`. Inside the callback every DB operation goes through the transaction-scoped `txApp` (never the captured outer `app`), avoiding the WAL-writer deadlock / `SQLITE_BUSY` pitfall:
   - Loads the wallet with `txApp.FindRecordById("wallets", walletId)`. If it is missing, returns `e.BadRequestError(...)` → 400 and the transaction rolls back (nothing persisted, wallet untouched).
   - Checks `wallet.GetFloat("balance") >= amount`; otherwise returns `e.BadRequestError("Insufficient funds", nil)` → 400 with rollback.
   - Debits the wallet: `wallet.Set("balance", balance-amount)` then `txApp.Save(wallet)`.
   - Sets the submitted `wallet`/`amount` (and leaves the optional `note` from the payload) on `e.Record`.
   - **Re-points `e.App` at `txApp`** before calling `e.Next()` so PocketBase's default save logic for the withdrawal record runs *inside the same transaction*. The original `e.App` is restored afterward. The success path returns `e.Next()` so the request chain is propagated (the v0.23+ requirement); any error from `RunInTransaction` rolls back both the balance change and the withdrawal row REDACTEDmatically.

The existing migration registration and collection schemas were left untouched, and the binary still builds/runs standalone: `go build -o wallet-app .` then `./wallet-app serve --http=0.0.0.0:8090`.
