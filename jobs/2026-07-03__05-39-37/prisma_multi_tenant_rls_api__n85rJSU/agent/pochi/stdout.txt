## What was done

**1. Prisma schema** (`prisma/schema.prisma`) — added the `Item` model:
```prisma
model Item {
  id       String @id @default(uuid())
  name     String
  tenantId String
}
```
Ran `prisma generate` + `prisma db push` to create the SQLite `dev.db`.

**2. Prisma 7 driver adapter** — Prisma 7 ships without built-in query engines, so a driver adapter is required. Installed `@prisma/adapter-better-sqlite3` (+ `better-sqlite3`) and wired it into the `PrismaClient` constructor using the `DATABASE_URL` from `.env`.

**3. `server.js`** (port 3000) with the RLS enforcement via `prisma.$extends`:
- A `tenantScopedPrisma` middleware reads the `x-tenant-id` header and builds a **per-request scoped Prisma client** using `basePrisma.$extends`. The extension's `query.item.$allOperations` hook intercepts **every** `item` operation:
  - For `create`/`createMany`/`upsert` → injects `tenantId` into `data`
  - For all read/update/delete operations → forces `tenantId` into the `where` filter
- This means handlers never touch `tenantId` directly — isolation is enforced at the data-access layer, so a handler can't accidentally leak or cross-write another tenant's data.
- `GET /items` → `findMany()` scoped to the requesting tenant.
- `POST /items` (body `{ name }`) → `create({ data: { name } })` with `tenantId` REDACTED-injected.
- Missing `x-tenant-id` header → `400`. Missing/empty `name` → `400`.

## Verification
- Created items for `tenantA` (Apples, Bananas) and `tenantB` (Carrots).
- `GET /items` with `x-tenant-id: tenantA` returned only Apples + Bananas; with `tenantB` returned only Carrots — even though the underlying DB contains all rows (confirmed by direct SQLite query). RLS isolation is real.
- Edge cases (missing header, missing name) return `400` as expected.
