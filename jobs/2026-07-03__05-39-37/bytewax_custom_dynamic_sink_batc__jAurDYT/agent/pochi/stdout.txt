## Summary

**`RotatingFileSinkPartition`** (subclass of `StatelessSinkPartition`):
- Receives the `worker_index`, `run_id`, and `output_dir` from the sink's `build` method.
- Tracks the current `part` number, the count of records in the current file, and a lazily-opened file handle.
- `write_batch` handles arbitrarily-sized batches by slicing the incoming list against the remaining capacity of the current file. When a file reaches exactly 20 records, it is flushed/closed, the part number increments, and subsequent records go to the next file. This correctly handles the case where a single batch spans multiple files (e.g. a 25-item batch with 15 records already in the file → 5 to current file, rotate, 20 to next file, rotate, remaining handled on next batch).
- Files are opened lazily so workers that receive no data don't create empty files.
- Writes JSON objects `{"worker": <worker_index>, "value": <value>}`, one per line.

**`RotatingFileSink`** (subclass of `DynamicSink`):
- `build(step_id, worker_index, worker_count)` instantiates a partition per worker, passing the `worker_index` so each worker writes to its own isolated files.

**Dataflow** (`flow`):
- `op.input` with `TestingSource(list(range(200)))` to generate the 200 integers.
- `op.redistribute` to spread the single-partition source across all 4 workers.
- `op.output` to the `RotatingFileSink`.
- Reads the run-id from `/logs/artifacts/run-id`.

Output files are written to `/home/user/bytewax-sink/out/` named `output-<run-id>-worker-<worker_index>-part-<part_number>.jsonl`.
