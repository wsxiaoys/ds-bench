# Local Asynchronous Document-Conversion Gateway ## Background A field-operations team needs an internal, fully offline HTTP gateway that turns document conversion into *managed asynchronous jobs*: clients submit documents, poll or stream progress, cancel work, and fetch results in several representations long after the conversion finished — even if the gateway process was restarted in between. You must build this gateway yourself, from scratch, on top of the pinned `docling` **2.107.0** library that is already installed in this container (its model weights are pre-baked locally). Do **not** use, wrap, proxy, or start any ready-made document conversion server product; the gateway, its queue, its worker model and its durable store are all yours to design and implement. The container has **no network access at runtime**. Every Python package you need (an ASGI web framework, an ASGI server and an HTTP client library among them) is already installed — do not attempt to install anything. ## Requirements * Accept conversion jobs from two different submission surfaces: an uploaded file, and a reference to a file already on the local disk. * Support an idempotency-key contract so that a retried submission never converts the same document twice. * Run conversions through a bounded worker/queue model with explicit, documented backpressure once the queue is saturated. * Expose a job state machine with timestamps and progress, plus job listing, cancellation, and a streaming progress feed. * Serve finished results in three different representations derived from the real conversion. * Persist job state and results so a restarted gateway keeps serving everything it already finished, and repairs jobs that were interrupted. * Return structured errors from a fixed error-code taxonomy, and expose health and metrics endpoints. ## Implementation Hints * Project path: `/home/user/project` * Start command (run with the project path as the working directory): `python service/main.py` * The gateway MUST bind **127.0.0.1** only, on the TCP port given by the environment variable `GATEWAY_PORT` (default `8077`), and MUST answer `GET /healthz` with HTTP 200 within 60 seconds of process start. Base URL below: `http://127.0.0.1:${GATEWAY_PORT}`. * Environment variables the gateway MUST honour: * `GATEWAY_PORT` — listen port, default `8077`. * `GATEWAY_STATE_DIR` — directory holding all durable state, default `/home/user/project/state`. It MUST be created if missing, and it MUST be the only place durable job data is written. * `GATEWAY_JOB_TIMEOUT_SECONDS` — per-job wall-clock budget measured from the moment the job starts running, default `120`. * On `SIGTERM` the process MUST exit within 10 seconds. * Fixed capacity model: **at most 2 jobs may be in state `running` at any moment**, and **at most 4 accepted-but-not-yet-started jobs may wait** in the queue. Waiting jobs MUST start in ascending `seq` order (FIFO). Serving any HTTP request (including `GET /healthz` and result reads) MUST NOT be blocked by running conversions: `GET /healthz` MUST answer in under 1 second even while both workers are busy and other clients are streaming. ### Job object Every endpoint that returns a job returns this exact JSON object (all keys always present): ```json { "job_id": "string, canonical UUID, unique per job", "seq": "integer, starts at 1, +1 per accepted job, never reused, survives restart", "state": "queued | running | succeeded | failed | cancelled", "source_kind": "upload | path", "source_name": "string, the base file name of the submitted document", "fingerprint": "string, lowercase sha256 hex digest of the exact document bytes", "pace_seconds": "number", "progress": "number in [0.0, 1.0], rounded to 2 decimals", "created_at": "RFC 3339 UTC timestamp ending in Z", "started_at": "RFC 3339 UTC timestamp ending in Z, or null", "finished_at": "RFC 3339 UTC timestamp ending in Z, or null", "duration_seconds": "number rounded to 3 decimals = finished_at - started_at, or null when either is null", "cancel_requested": "boolean", "error": "null, or {\"code\": string, \"message\": non-empty string}" } ``` Progress rules: exactly `0.0` while `queued`; strictly greater than `0.0` and strictly less than `1.0` while `running`; exactly `1.0` when `succeeded`; any value in `[0.0, 1.0]` when `failed` or `cancelled`. `pace_seconds` is a client-supplied throttle used for load rehearsals: the worker MUST hold the job in state `running` for that many seconds **before** the conversion begins. That waiting time counts as running time and counts toward `GATEWAY_JOB_TIMEOUT_SECONDS`. Accepted range: `0 <= pace_seconds <= 30`; default `0`. ### Endpoints * `POST /v1/jobs/upload` — `multipart/form-data` with a required part named `file` (binary, carrying a filename) and an optional part named `pace_seconds`. Optional request header `Idempotency-Key`. * `POST /v1/jobs/path` — `application/json` body `{"source_path": "", "pace_seconds": <number, optional>}`. Optional request header `Idempotency-Key`. Only paths inside `/home/user/project/assets` may be read; anything else (including paths that merely traverse or point outside it) MUST be refused with `403 PATH_NOT_ALLOWED`, which MUST be decided **before** existence is considered. A permitted path that does not point at an existing regular file MUST yield `404 SOURCE_NOT_FOUND`. * Both submission endpoints return **201** with the job object for a newly accepted job. Neither may reject a submission because of the document's extension, media type, or content: format problems surface as a failed job, never as a rejected submission. * Idempotency: when `Idempotency-Key` is present and that key was already used, the gateway MUST return **200** with the *original, unchanged* job object and MUST NOT enqueue or perform another conversion; if the replay carries a document whose `fingerprint` differs from the stored one, it MUST fail with `409 IDEMPOTENCY_KEY_CONFLICT` and MUST NOT create a job. Keys are global across both submission endpoints and survive a restart. A submission **without** the header always creates a new job, even for byte-identical content. * Backpressure: a submission that would exceed the 4-slot queue MUST be rejected with **429** `QUEUE_FULL` and a `Retry-After` response header holding an integer number of seconds `>= 1`. An idempotent replay of a known key MUST still succeed with 200 even while the queue is full. * `GET /v1/jobs/{job_id}` — **200** with the job object, or `404 JOB_NOT_FOUND`. * `GET /v1/jobs?state=<state>&limit=<n>` — **200** with `{"count": <integer>, "jobs": [<job object>, ...]}`, ordered by `seq` **descending**, `count` equal to the number of returned jobs. `state`, when present, filters to that state and MUST be one of the five states. `limit` is an integer in `[1, 100]`, default `50`. A malformed `state` or `limit` MUST yield `400 VALIDATION_ERROR`. * `GET /v1/jobs/{job_id}/result?format=<markdown|json|chunks>` — `format` defaults to `markdown`; any other value MUST yield `400 INVALID_FORMAT`. Every successful result response MUST carry the response header `X-Job-Id` holding the job id. * `markdown` — **200**, `Content-Type` beginning with `text/markdown`, body being the converted document rendered as Markdown. * `json` — **200**, `application/json`, body `{"job_id": "...", "format": "json", "document": { ... }}` where `document` is the converted document's own complete structured dictionary representation. * `chunks` — **200**, `application/json`, body `{"job_id": "...", "format": "chunks", "count": <integer>, "chunks": [ ... ]}`. Each chunk object has exactly the keys `index` (integer, starting at 0, ascending, contiguous), `text` (non-empty string), `headings` (array of strings — the section-heading trail the chunk sits under, possibly empty, every entry also appearing in the Markdown representation), and `char_len` (integer, equal to the length of `text`). Chunks MUST be produced by document-structure-aware chunking of the converted document, not by slicing raw text, and MUST NOT require downloading any tokenizer or model. * Requesting a result for a job in state `queued` or `running` MUST yield `409 JOB_NOT_FINISHED`; for a job in state `failed` or `cancelled`, `409 RESULT_UNAVAILABLE`. * `POST /v1/jobs/{job_id}/cancel` — * job is `queued`: **200** with the job object already in state `cancelled`; the conversion MUST never run. * job is `running`: **202** with the job object, `cancel_requested` set to `true`. If the job is still inside its `pace_seconds` window the conversion MUST NOT start and the job MUST end in state `cancelled`; in any case the job MUST reach a terminal state within 15 seconds of the request. * job already terminal: `409 JOB_ALREADY_TERMINAL`. * `GET /v1/jobs/{job_id}/events` — a newline-delimited JSON stream with `Content-Type` beginning with `application/x-ndjson`. Each line is one JSON object with exactly the keys `seq` (integer, starting at 0 and incrementing by 1 per line **within this stream**), `job_id`, `state`, `progress`, and `ts` (RFC 3339 UTC timestamp ending in `Z`). The first line MUST be emitted within 2 seconds and MUST reflect the job's current state; a new line MUST be emitted whenever `state` or `progress` changes; `progress` MUST never decrease; and the stream MUST end by itself right after emitting a line whose `state` is terminal (so an already-terminal job yields exactly one line and then the response ends). An unknown job id MUST yield `404 JOB_NOT_FOUND` as a normal JSON error response. * `GET /healthz` — **200** with `{"status": "ok", "workers": 2, "queue_capacity": 4, "queue_depth": <integer>, "running": <integer>, "uptime_seconds": <number>}`. * `GET /metrics` — **200** with exactly the integer-valued keys `submitted`, `succeeded`, `failed`, `cancelled`, `rejected_queue_full`, `idempotent_hits`, `queued_now`, `running_now`. `submitted` counts every accepted job ever (idempotent replays excluded); `succeeded`, `failed` and `cancelled` count jobs currently in those terminal states; these four MUST be derived from the durable store and therefore survive a restart. `rejected_queue_full` and `idempotent_hits` are per-process counters that reset on restart. `queued_now` and `running_now` are the current queue depth and running count. ### Errors Every response with a status code outside 2xx MUST have `Content-Type: application/json` and the body `{"error": {"code": "<CODE>", "message": "<non-empty string>"}}`, using only these codes: `VALIDATION_ERROR` (400), `INVALID_FORMAT` (400), `PATH_NOT_ALLOWED` (403), `SOURCE_NOT_FOUND` (404), `JOB_NOT_FOUND` (404), `IDEMPOTENCY_KEY_CONFLICT` (409), `JOB_NOT_FINISHED` (409), `RESULT_UNAVAILABLE` (409), `JOB_ALREADY_TERMINAL` (409), `QUEUE_FULL` (429). A missing `file` part, a missing/blank `source_path`, a non-numeric `pace_seconds`, or a `pace_seconds` outside `[0, 30]` are all `VALIDATION_ERROR`. Job-level failures are reported in the job object's `error` field with one of exactly these codes: `CONVERSION_FAILED` (the document could not be converted), `JOB_TIMEOUT` (the running budget was exceeded), `INTERRUPTED` (the job was still `queued` or `running` when the process stopped). ### Durability All job records, idempotency keys and finished results MUST outlive the process. After a restart with the same `GATEWAY_STATE_DIR`, previously `succeeded` jobs MUST still be listable and MUST still serve all three result representations byte-for-byte, and every job that was persisted as `queued` or `running` MUST be repaired at startup into state `failed` with `error.code` `INTERRUPTED` and a non-null `finished_at`.

- **app.py** – all required FastAPI routes (`/v1/jobs/upload`, `/v1/jobs/path`, get/list/cancel/result/events, `/healthz`, `/metrics`) plus global exception handlers mapping validation/API errors to the exact JSON error envelope.
- **main.py** – binds `127.0.0.1:${GATEWAY_PORT}` only, uses `uvicorn`'s `timeout_graceful_shutdown` for a bounded SIGTERM exit.
