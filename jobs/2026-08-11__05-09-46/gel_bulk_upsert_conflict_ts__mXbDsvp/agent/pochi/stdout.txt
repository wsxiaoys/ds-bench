# Idempotent Bulk Catalog Sync (Gel + TypeScript) ## Background An e-commerce team receives product catalogs from upstream suppliers as batches of JSON records. The catalog itself lives in a local **Gel 6** instance (the graph-relational database formerly known as EdgeDB). Today the import is a hand-written loop that creates duplicate categories, silently doubles products when a batch is replayed, and leaves half-imported data behind when one record is rejected. Your job is to replace it: model the catalog in Gel's schema language, get that schema into the database through Gel's migration engine, and build a re-runnable synchronisation CLI in TypeScript on top of the official `gel` npm client. The CLI must be able to ingest the same batch any number of times without changing the database after the first successful run, and it must tell the operator, per record, what actually happened. ## Requirements - Define the catalog data model in the project's Gel schema and apply it to the running instance through a migration, so that the instance's migration state is in sync with the files on disk. - Implement a batch synchronisation CLI that reads a JSON batch file and, for every record, either creates a product or brings the existing product in line with the record. - Resolve the objects a product points to (its category, its tags) on demand: they are created when they are not there yet, reused otherwise, and never duplicated — no matter how many records in the batch (or how many previous runs) reference the same name. - Classify every record's outcome and report it, together with per-batch totals, as machine-readable output. - Apply the whole batch atomically: either every record in the batch lands, or none does. - Reject malformed batches with a documented, machine-readable error contract, without touching the database. ## Implementation Hints - Project path: `/home/user/catalog-sync`. Work inside it; the Gel project directory (`gel.toml`, `dbschema/`) is already there and already linked to the local instance `local_gel`, so client connection details are discovered from the project directory — do not introduce connection environment variables, DSNs, or credentials of your own. - The local Gel instance is not running when you start. Start it with `/usr/local/bin/gel-start.sh` (idempotent, must be run as `root`; it returns once the instance answers queries, which can take up to ~30 s). - Treat the environment as offline. Every dependency you need is already installed under `/home/user/catalog-sync/node_modules` (including the pinned `gel` client and TypeScript); do not run `npm install`/`npm ci`, do not upgrade anything, and do not add dependencies. - Command: `node dist/sync.js --input <path/to/batch.json>`, executed with the working directory `/home/user/catalog-sync`. `/home/user/catalog-sync/dist/sync.js` must already exist and run as-is — verification never builds the project for you. - Schema: module `default` must contain object types named exactly `Category`, `Tag` and `Product` with these pointers (all names exact, in module `default`): - `Category`: required property `name` of type `str`, unique across all `Category` objects. - `Tag`: required property `label` of type `str`, unique across all `Tag` objects. - `Product`: required property `sku` of type `str`, unique across all `Product` objects; required property `name` of type `str`; required property `price_cents` of type `int64` that rejects negative values; required property `stock` of type `int64` that accepts `0`..`100000` inclusive and rejects any value outside that range; a required single link `category` to `Category`; and a `multi` link `tags` to `Tag`. - Batch file format — a JSON array of record objects: ```json [ { "sku": "non-empty string", "name": "non-empty string", "price_cents": 0, "stock": 0, "category": "non-empty string", "tags": ["non-empty string"] } ] ``` `price_cents` and `stock` are integers `>= 0`. `tags` is optional; when it is absent the record has no tags. An empty array is a valid batch. - Sync semantics: a product is identified by its `sku`; `category` and each entry of `tags` identify a `Category` by `name` and a `Tag` by `label`. After a successful run a product's `tags` links must be exactly the de-duplicated set named by its record — tags no longer named are unlinked, while `Tag` and `Category` objects themselves are never deleted. A record's outcome is `inserted` when no product with that `sku` existed before this run, `updated` when it existed but at least one of `name`, `price_cents`, `stock`, its category name or its tag set differed from the record, and `unchanged` when everything already matched. Consequently, re-running a batch that was already applied must report every record as `unchanged` and must neither create nor modify any object. - The batch must reach the server as set-based work parameterised by the batch data (one JSON parameter for the whole batch), not as one query per record, and it must run inside a client-managed transaction with the client's automatic retry behaviour. - Success output: exit code `0` and exactly one JSON document on stdout (nothing else on stdout; put any human-readable logging on stderr): ```json { "ok": true, "total": 3, "inserted": 2, "updated": 1, "unchanged": 0, "results": [ {"sku": "A-1", "outcome": "inserted", "category": "tools", "tags": ["metal", "sale"]} ] } ``` `total` is the number of records in the batch, `inserted`/`updated`/`unchanged` are the outcome counts, and `results` holds one entry per record sorted by `sku` in ascending lexicographic order, where `outcome` is one of `inserted`/`updated`/`unchanged`, `category` is the record's category name and `tags` is the de-duplicated tag list sorted in ascending lexicographic order. - Failure output: exactly one JSON document on stdout shaped `{"ok": false, "error_code": "<code>", "message": "<non-empty string>"}` plus the matching exit code: - exit `2`, `error_code` `input_unreadable`: no `--input` argument was given, the file does not exist, or its content is not valid JSON. - exit `3`, `error_code` `invalid_record`: the top-level JSON value is not an array, or some record violates the batch format above. Add the key `index` holding the 0-based position of the first offending record, or `null` when the top-level value itself is not an array. - exit `4`, `error_code` `duplicate_sku`: the same `sku` appears in more than one record. Add the key `sku` holding the first `sku` that repeats. Record-format validation takes precedence over duplicate detection. - exit `5`, `error_code` `db_error`: the database rejected the batch (for example a value the schema forbids). In every failure case, including `db_error`, the database contents must be exactly what they were before the invocation. - A batch of 200 records must be processed within 60 seconds.
