**Architecture & Key Design Decisions:**

1. **Typesense-backed ranking**: All leaderboard state is persisted in a `leaderboard` collection in Typesense. On startup, the collection is created if it doesn't exist and seeded with the 5 initial players. Rankings are derived from live Typesense queries sorted by `score:desc,name:asc`.

2. **Concurrency correctness**: Uses a per-player mutex (promise-chain-based lock) to serialize concurrent score updates for the same player. Each update performs a read-modify-write cycle: fetch current document → compute `newScore = currentScore + delta` → update document. The lock ensures no lost updates even under high concurrency (verified with 20 concurrent updates to the same player).

3. **Live updates**: Server-Sent Events (SSE) at `/api/events` notify all connected browsers when any score changes. The frontend listens for SSE events and re-fetches the leaderboard, keeping all clients in sync within seconds without page reloads.

4. **API endpoints**:
   - `GET /` — HTML page with all required `data-testid` attributes
   - `GET /api/leaderboard` — JSON array ordered by rank with `rank`, `player_id`, `name`, `score`
   - `POST /api/score` — Accepts `{"player_id": string, "delta": integer}`, returns updated player; 400 for invalid input, 404 for unknown player
