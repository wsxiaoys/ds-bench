### Implementation Details:
1. **Lease-based Leader Election**:
   - The coordinator (`IndexerCoordinator`) utilizes the local etcd v3 HTTP/JSON gRPC-gateway (`http://127.0.0.1:2379`) to grant a lease with a bounded TTL.
   - It executes an atomic compare-and-create transaction on a single election key, checking if `create_revision == 0` (i.e., the key does not exist).
   - If successful, it retrieves the `create_revision` of the newly created election key, which serves as a globally-monotonic, strictly increasing **fencing token** across terms.
   - A background thread automatically keeps the lease alive via `keepalive` requests. If keepalive fails or if etcd indicates that the lease has expired, the coordinator automatically steps down.

2. **Fencing & Maintenance**:
   - Only the elected leader can execute `run_maintenance()`.
   - Before performing any LanceDB operations, the coordinator performs a live check against etcd to verify that it still owns the election key with the current term's fencing token. If not, it raises a `PermissionError`.
   - The maintenance routine calls `table.optimize()`, which compacts small fragments and rebuilds/updates the vector index.
   - It reads and returns the table state before and after maintenance, including the fencing token, versions, and unindexed row counts.

3. **Failovers & Crash Simulation**:
   - **Graceful Failover**: `resign()` deletes the election key and revokes the lease, allowing followers to immediately acquire leadership.
   - **Ungraceful Failover**: `simulate_crash()` stops lease keepalives without revoking/deleting the key, allowing the lease to expire after its TTL before followers can take over.
