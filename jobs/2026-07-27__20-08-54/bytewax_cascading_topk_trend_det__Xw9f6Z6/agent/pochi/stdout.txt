# Cascading Top-K & Trend Detection over Event-Time Windows (Bytewax) ## Background You are building a real-time analytics pipeline with **Bytewax** (`bytewax==0.21.1`), a Python-native stateful stream-processing framework. The pipeline ingests a stream of item "impression" events and must produce two analytics feeds by chaining an event-time windowed aggregation into a downstream stateful stage: a global **top-K** ranking and a **trending-items** feed. Everything runs locally. No Kafka, no databases, no network access. ## Requirements Implement a single Bytewax dataflow that, when executed, reads the input event stream, performs a two-stage cascading computation, and writes two JSONL output files. **Stage 1 — per-item counts per event-time window.** Group events into **tumbling windows of exactly 60 seconds** using **event time** taken from each event's `ts` field, aligned to the instant `2024-01-01T00:00:00+00:00`. The integer **window index** of a window is the number of whole 60-second intervals between the alignment instant and the window's start (the window covering `[00:00:00, 00:01:00)` is index `0`, the next is `1`, and so on). For every item and every window in which that item has at least one event, compute the count of that item's events in that window. **Stage 2 — rolling history, top-K, and trend detection (stateful, fed by Stage 1).** Consume the Stage-1 per-window counts and maintain, per item, a rolling history of that item's most recent **N = 3** window results (a window result is a `(window index, count)` pair; only windows in which the item actually appears are recorded). From this produce: - **Global Top-K feed** (`K = 3`): rank items by their **rolling total** — the sum of the counts in the item's most recent (up to) `N` recorded window results. Ranking is by rolling total descending; ties are broken by item name ascending. Emit the top `K` items (fewer only if fewer than `K` distinct items exist). - **Trending feed**: for each item, consider its window results in ascending window-index order. The **growth** of a window result is its count minus the count of that item's immediately preceding recorded window result (the previous element in the item's ordered sequence of non-empty windows, regardless of any gap in window indices). An item's first recorded window result has no growth. A window result is *trending* when its growth is **strictly greater than 5**. ## Implementation Hints - Project path: `/home/user/project` - Input events: `/home/user/project/data/events.jsonl`. The order of lines is not significant. - Use `bytewax==0.21.1`. All counts, totals, growth values, ranks, and window indices are integers.

import json
from datetime import datetime, timezone
from collections import defaultdict

align = datetime(2024,1,1,tzinfo=timezone.utc)
counts = defaultdict(lambda: defaultdict(int))
with open('data/events.jsonl') as f:
    for line in f:
        line=line.strip()
        if not line: continue
        o = json.loads(line)
        ts = datetime.fromisoformat(o['ts'])
        wid = int((ts-align).total_seconds()//60)
        counts[o['item']][wid]+=1

summaries = {}
trending=[]
for item, wc in counts.items():
    windows = sorted(wc.items())
    prev=None
    for wid,c in windows:
        if prev is not None:
            growth = c-prev
            if growth>5:
                trending.append((item,wid,c,prev,growth))
        prev=c
    last3 = windows[-3:]
    total = sum(c for _,c in last3)
    summaries[item]=total

ranked = sorted(summaries.items(), key=lambda p:(-p[1],p[0]))
print('TOPK expected:')
for i,(it,tot) in enumerate(ranked[:3]):
    print(i+1, it, tot)
print('TRENDING expected:')
for t in trending:
    print(t)
print()
print('all totals', ranked)

Implemented the Bytewax dataflow at `/home/user/project/pipeline.py`:

**Stage 1** uses `bytewax.operators.windowing.count_window` with an `EventClock` (keyed on each event's `ts`) and a `TumblingWindower` (60s length, aligned to `2024-01-01T00:00:00+00:00`). Bytewax's tumbling-window ID (`since_origin // length`) is exactly the required window index, so `count_window` directly yields `(item, (window_index, count))` for every item/window with ≥1 event.

**Stage 2** is a stateful, batch-final computation fed by Stage 1:
- `op.fold_final` collects all `(window_index, count)` results per item (only emitted once, at EOF, since this is a finite batch source).
- For each item, the collected results are sorted ascending by window index (defensive against any arrival-order edge cases), then:
  - Trending records are derived by comparing each window's count to the immediately preceding recorded window's count (growth strictly > 5).
  - The rolling total is the sum of counts from the last (up to) N=3 window results.
- The trending records are flattened directly into `out/trending.jsonl`.
- The per-item rolling totals are re-keyed to a single group, collected again with `op.fold_final`, ranked (rolling total desc, item name asc), and the top K=3 are flattened into `out/topk.jsonl`.

Both output streams are keyed (required for `FixedPartitionedSink` routing) and written via `FileSink`, which truncates/recreates the file on each run, so the pipeline is safely re-runnable.
