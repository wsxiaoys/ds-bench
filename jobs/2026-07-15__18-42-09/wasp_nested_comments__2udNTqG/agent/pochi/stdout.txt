# Threaded (Nested) Comments in Wasp ## Background You are building a discussion feature for a small full-stack app using [Wasp](https://wasp.sh) (a React + Node.js + Prisma framework). A Wasp project scaffold already exists at the project path with the Wasp CLI installed. The app must support threaded comments where any comment can be a reply to another comment, forming an arbitrarily deep tree. Comments belong to a post and are written by a user. ## Requirements Implement a threaded comment system with these data models, operations, seed data, and a page: - **Data model** (`schema.prisma`): keep the default SQLite datasource. Define at least: - `User` with a unique `username` field. - `Post` with a `title` field. - `Comment` with `content`, a relation to its `Post`, a relation to its author `User`, and a **self-referential** optional `parent` relation to another `Comment` (with a `children` back-relation). This models the reply tree. - **Operations** (Wasp `query`/`action` declarations, callable on the client and auto-exposed on the server): implement exactly these four, with these exact names: - `getPosts` (query): returns every post. - `getCommentTree` (query): given a post, returns that post's comments as a nested tree (top-level comments, each with their replies nested recursively to any depth). - `createComment` (action): creates a comment on a post, authored by a user (looked up by username), optionally as a reply to an existing comment. - `deleteComment` (action): deletes a comment AND all of its descendant replies (cascade), so no orphaned replies remain. - **Seed**: define a Wasp seed function importable as `devSeed` (runnable via `wasp db seed devSeed`) that idempotently creates users with usernames `alice` and `bob`, and a post titled `Wasp Nested Comments`. Running it more than once must not create duplicates. - **Page**: a route `/post/:postId` whose page renders the nested comment thread for that post, showing every comment's text content. ## Implementation Hints - Project path: `/home/user/nested-comments` - Start command: `wasp start` (this runs the client on port 3000 and the server on port 3001). Before starting, apply migrations with `wasp db migrate-dev` and run `wasp db seed devSeed`. - Wasp automatically exposes each operation on the server at `POST http://localhost:3001/operations/<kebab-cased-operation-name>` (e.g. `getCommentTree` -> `/operations/get-comment-tree`), so the operation names above must match exactly. - Model the reply tree with a Prisma self-relation on `Comment` (an optional `parentId` foreign key plus a `children` list). Build the nested tree in `getCommentTree` recursively. - Deleting a comment must remove the whole subtree beneath it; you can achieve this with a Prisma `onDelete: Cascade` referential action on the self-relation or by deleting descendants explicitly. - Operation argument and result shapes (these are checked exactly): - `getPosts` takes no arguments and returns a JSON array; each element must include the keys `id` (number) and `title` (string). - `createComment` takes `{ postId: number, authorUsername: string, content: string, parentId?: number | null }`. When `parentId` is omitted or null the comment is a top-level comment; otherwise it is a reply to that comment. It must return the created comment object, which must include its `id` (number). - `getCommentTree` takes `{ postId: number }` and returns a JSON array of the post's top-level comment nodes (those with no parent). Every node in the tree (at every depth) must be an object with exactly these keys: `id` (number), `content` (string), `authorUsername` (string, the username of the comment's author), `parentId` (number or null), and `children` (an array of child comment nodes in the same shape). Sibling nodes must be ordered by ascending `id` at every level. - `deleteComment` takes `{ commentId: number }`. - The `/post/:postId` page must display the `content` text of each comment in the post's thread.
