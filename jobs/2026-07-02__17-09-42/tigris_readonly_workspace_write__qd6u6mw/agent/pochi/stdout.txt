# ReadOnly Workspace Write Denial with Tigris Agent Kit ## Background Tigris Agent Kit (`@tigrisdata/agent-kit`) provisions per-agent workspaces with TTL and **scoped IAM credentials**. A workspace's scoped credentials carry one of two roles: `Editor` (read+write) or `ReadOnly` (read only). To prove that scoped credentials actually enforce role boundaries, this task drives a real Tigris workspace through an editor-write, then mints a second set of `ReadOnly` credentials and demonstrates that those credentials can read existing objects but are denied when they try to write a new object. Because `createWorkspace` only mints a single scoped key per call and the documented Agent Kit way to produce additional scoped credentials for the same dataset is `createForks` (which performs a copy-on-write snapshot of the source bucket and provisions per-fork scoped credentials), you will: 1. Create the editor workspace with snapshots enabled. 2. Write `notes/welcome.txt` into the editor workspace using the editor credentials. 3. Use `createForks(... , 1, { credentials: { role: "ReadOnly" } })` to mint a single `ReadOnly` fork of the same data — the fork's scoped credentials are the **second** set of credentials referenced in the requirements, scoped to a copy-on-write view of the workspace contents. 4. Use those ReadOnly credentials to attempt a forbidden write **and** a successful read against the fork bucket. 5.
