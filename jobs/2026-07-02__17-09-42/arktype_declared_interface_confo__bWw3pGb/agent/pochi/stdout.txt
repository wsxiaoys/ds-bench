Wired two ArkType 2.2 schemas to the `Product` interface in `/home/user/myproject`, plus the entry-point that runs the validation.

## Files created

**`schema.ts`** — valid schema, default-exported for `import productSchema from "./schema"`:
```ts
import { type } from "arktype";
import type { Product } from "./types";

const productSchema = type.declare<Product>().type({
    id: "string",
    sku: "string",
    price: "number",
    tags: "string[]"
});

export default productSchema;
```

**`broken.ts`** — same shape but omits `tags`, so `type.declare<Product>()`'s structural check rejects it at compile time:
```ts
import { type } from "arktype";
import type { Product } from "./types";

const brokenProductSchema = type.declare<Product>().type({
    id: "string",
    sku: "string",
    price: "number"
});

export default brokenProductSchema;
```

**`index.ts`** — runs `productSchema.assert(samplePayload)` and prints `Validated product: <id>` to stdout:
```ts
import productSchema from "./schema";

const samplePayload = {
    id: "prod-001",
    sku: "SKU-12345",
    price: 199.99,
    tags: ["electronics", "gadget"]
} as const;

const validated = productSchema.assert(samplePayload);

console.log(`Validated product: ${validated.id}`);
```

`types.ts` was not touched, and the pre-existing `tsconfig.json` already had `"exclude": ["node_modules", "broken.ts"]`, so the project type-checks cleanly.

## Note on the call form

The task spec literally wrote `type.declare<Product>()({...})`, but in ArkType 2.2 `type.declare<T>()` returns `{ type: TypeParser }` (see `node_modules/arktype/out/scope.js` and `declare.d.ts`), which is **not** itself callable. The canonical form documented at https://arktype.io/docs/declare and shown in the package's exported `.d.ts` is `type.declare<T>().type(def)`. Writing `type.declare<Product>()({...})` directly produces a TypeScript error and prevents the schema from being "valid". I therefore used the actually-compiling API `type.declare<Product>().type({...})` in both `schema.ts` and `broken.ts`; the structural conformance check from `type.declare<Product>()` is what causes `broken.ts` to fail compilation, which is the behavior the task is asking to demonstrate. If you specifically need the literal `()({...})` shape, that would require either downgrading to an ArkType version whose parser exposed a callable `declare` return, or wrapping `type.declare<Product>().type` in a thin helper — happy to switch to either if that's the intent.
