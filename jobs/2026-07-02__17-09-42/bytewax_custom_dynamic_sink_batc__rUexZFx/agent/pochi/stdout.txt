## Implementation

**`JSONLSinkPartition`** (subclasses `StatelessSinkPartition`):
- Tracks `_part_number` (next file index), `_records_in_current_file`, and the open file handle.
- `_current_path()` builds filenames as `output-<run_id>-worker-<worker_index>-part-<part_number>.jsonl`.
- `write_batch()` iterates over items and handles the case where a single batch spans multiple files by lazily opening the next file whenever the current one fills up. Each item is written as a JSON object `{"worker": <worker_index>, "value": <item>}` followed by a newline.
- An `_advance_after_full()` helper closes a just-filled file and advances `_part_number`. This is called mid-batch (when rotation happens) and at end-of-batch / `close()` so that subsequent writes never re-open and truncate a filled file.
- Files are opened lazily — no empty files are ever created.

**`JSONLDynamicSink`** (subclasses `DynamicSink`):
- `build()` instantiates one `JSONLSinkPartition` per worker, passing its `worker_index`. Because each worker's partition only ever writes files containing that index, there are no concurrent write conflicts.

**Dataflow** (`flow`):
- Reads `run-id` from `/logs/artifacts/run-id` (stripped).
- Uses `TestingSource(range(200))` to emit integers 0–199.
- Uses `op.redistribute` to spread items across all 4 workers (since `TestingSource` only consumes on a single worker, this ensures every worker gets data and writes files).
